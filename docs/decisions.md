# 为什么这样配

## 先能看懂，再逐步加入功能

`minimal` 保留原生 Pi，便于学习和排查问题。`recommended` 集中处理界面和几个高频操作。`personal` 展示我的完整工作流，包含更多工具、网络功能和供应商偏好。三者使用独立目录，可以比较和退出。

这也给讨论提供了基准：报告问题时，先说明在哪种配方出现，以及最小需要哪几个扩展。

## 界面各负其责

HUD 的价值在于会话状态、上下文和用量的持续可见；Block Editor 改善输入区域及欢迎页；CC 改善工具输出。关闭 CC 的重复界面后，这三者能组成一套一致的体验。`markdown.mermaid: final` 沿用日常选择，等待完整图表后渲染。

HUD 的上下文、费用、速度等数值各有统计边界，并非账单或服务商控制台的替代。详见原 HUD 的[统计说明](https://github.com/M1racleShih/pi-hud#readme)。

## 模型选择和清空会话

模型较多时，按提供商分组比在长列表中查找更顺手。将原生模型选择器移到 `Ctrl+Alt+L`，把 `Ctrl+L` 留给分组选择器。原生 `/model` 保留，便于出现兼容问题时切回。

我常在保持模型和思考级别的前提下清空任务上下文，所以提供 `/clear`。原生 `/new` 的行为保持由 Pi 自己定义，使用者可以明确选择。

## 固定 Pi 和扩展版本

扩展需要与 Pi 的生命周期、事件结构和终端界面接口兼容。固定 Pi 1.2.0 和经过测试的扩展版本，才能在其他环境复现同一套组合。npm 生命周期脚本禁用，安装依赖依靠已发布文件和平台预编译包。

普通使用者可以直接安装官方 Pi，再按需选择扩展。仓库里的固定版本服务于完整复现和维护；它同样来自官方发布包，无需另装全局 Pi。

两个自有扩展尚不能从 npm 取得对应版本，因此用精确 Git 提交归档；其完整性值进入 npm 锁文件。HUD 当前工作区包含未发布改动，先保存仅含运行源码的快照，未来再换成包含所需功能的独立发布版。

## 保留个人偏好的边界

`personal` 的 Codex 默认模型、475000 上下文覆盖、25001 预留 token，以及 selected-models 中的模型参数，来自我的实际使用。这些值依赖模型与提供商，不是所有用户都适用。推荐配方不强制这些参数。

私有端点由用户环境提供；额度查询的组织、项目和账号信息不进入共享模板。自动标题、网页总结和 goal 的附加请求写在文档中，使用者可以明确选择。
